# 第三轮修复验证

日期：2026-09-07。包含上一轮尚未下载的隐藏系统列修复，以及第三轮新增的rowcount修复。
报告中的3个失败实例对应2类问题：唯一约束在两条路线失败，INSERT rowcount仅在psycopg3失败。

## 1. 隐藏系统列

客户仍使用上一版方言，所以两条路线继续出现 `constraint_reflected=False`。
当前B/M唯一约束按 `pg_constraint.conkey` 返回逻辑列；索引按负attnum排除
系统属性，不按列名黑名单误删真实用户列。single/multi入口均已覆盖。
细节见[隐藏系统列反射修复](隐藏系统列反射修复.md)。

## 2. INSERT rowcount=-1

本地复现第三轮原用例；新增边界用例也复现实际插入1行却返回-1，以及实际0行却返回-1。
`after_cursor_execute` 事件中驱动已经返回正确计数，问题发生在随后游标关闭阶段：

1. gaussdb.executemany按服务端command_tuples累加，不是按参数数量猜测。
2. SQLAlchemy默认不会为所有INSERT保留rowcount，普通INSERT结果会软关闭游标。
3. gaussdb游标关闭将内部rowcount重置为-1。
4. 本方言没有预先保存，应用稍后读SQLAlchemy Result时得到-1。

这是本项目方言对游标生命周期的适配缺口，不是“psycopg3纯Python实现无法批量计数”，
也不意味着SQLAlchemy违反了其通用INSERT rowcount约定。

新增 `GaussDBExecutionContext.post_exec`，在普通非RETURNING INSERT关闭游标前
保存实际 `cursor.rowcount`；M上下文也继承该行为，且保留LAST_INSERT_ID逻辑。
实际0和未知-1原样保留，不以参数数量或INSERT语句数量填值；不覆盖已有计数。
RETURNING、INSERTMANYVALUES分页、UPDATE/DELETE及文本语句保留原有结果处理。

## 4. 内网更新

本次两类修复均在方言层，保持已经跑通的底层psycopg2或gaussdb及动态库配置不变。
只需构建/安装新版方言wheel：

```bash
python -m build --wheel gaussdb_sqlalchemy
python -m pip install --force-reinstall --no-deps \
  gaussdb_sqlalchemy/dist/gaussdb_sqlalchemy-0.1.0-py3-none-any.whl
```

版本号仍为0.1.0，不能只凭版本号或文件大小判断是否更新；必须强制重装并重启Python进程。
依赖和动态库先按[双驱动启动指导](Linux双驱动启动.md)准备，按路线设置对应GAUSSDB_TEST_URL：

```bash
# 一次只配置当前路线的B或M测试库；以下包含客户原始唯一约束用例。
bash gaussdb_sqlalchemy/tools/run_driver_test.sh psycopg3 \
  -k 'rowcount or unique_constraint or index_reflection'
# 切换psycopg2独立环境及URL后：
bash gaussdb_sqlalchemy/tools/run_driver_test.sh psycopg2 \
  -k 'rowcount or unique_constraint or index_reflection'
```

去掉筛选会运行26基础+6专项共32条。客户原始唯一约束用例若在建表时被
GTM-Lite/全局二级索引限制阻止，要单独报告，不得算作反射通过。
