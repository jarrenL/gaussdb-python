# 隐藏系统列反射修复

日期：2026-09-07。针对第二轮报告的 `constraint_reflected=False`。

## 原因和改动

报告的数据库原始值为MYSQL，方言识别为B，模式识别正确。
旧B模式的唯一约束反射仍委托给PostgreSQL父类，父类按底层索引的indkey取列，
把分布式物理索引追加的系统属性误当成业务约束列。因此conkey只有 `[2]`，
反射却返回code及xc_node_hash、ctid、xmin、xmax。

- B/M的 `get_unique_constraints` 与 `get_multi_unique_constraints` 统一按
  `pg_constraint.conkey` 取逻辑列，保持复合列顺序和约束comment。
- 两条索引反射路径均剔除负attnum系统属性，保持原有表达式槽位处理。
  不按名称黑名单删除：正attnum的真实用户列即使同名，也必须保留。
- 空filter_names列表不再误触发全库唯一约束遍历。
- 不改变MYSQL/B与M的模式映射，不修改底层驱动或系统动态库。
- A/PG唯一约束仍委托原父类；此前A主键反射触发服务端段错误的问题未在本次修复。

本地只读目录查询确认xc_node_hash=-11、xc_node_id=-8、tableoid=-7。
专项真实库用例断言唯一约束、复合顺序、重复插入IntegrityError，以及唯一约束
和索引的single/multi四种返回结果。测试对象使用UUID名称并在finally中清理。

限制：本地专项的唯一约束包含分布键，不依赖全局二级索引；客户报告中自动追加
系统列的具体全局索引场景，由目录形状单测复现，尚未在客户x86_64/Python 3.12
环境完成复测。不能把上述8条专项通过称为客户26条全过或全量矩阵验收通过。

## 内网更新和复测

本次仅重新构建并安装方言wheel，底层psycopg2/gaussdb无需为这个bug更换：

```bash
python -m build --wheel gaussdb_sqlalchemy
python -m pip install --force-reinstall --no-deps \
  gaussdb_sqlalchemy/dist/gaussdb_sqlalchemy-0.1.0-py3-none-any.whl
```

方言版本号仍为0.1.0，应强制重装并重启测试Python进程，避免继续使用旧包。
按[双驱动启动指导](Linux双驱动启动.md)配置驱动、配套库和测试URL后：

```bash
# 选择已确认的B或M测试库；包含客户原始唯一约束用例、索引用例和增强专项。
bash gaussdb_sqlalchemy/tools/run_driver_test.sh psycopg2 \
  -k 'unique_constraint or index_reflection'
```

psycopg3须先通过驱动加载检查，再将路线参数改为psycopg3执行；
本次SQL反射修复不代表内网psycopg3的动态库加载问题也已解决。
若客户原始用例在建表时被GTM-Lite/全局二级索引能力限制阻止，须单独记录，
不能记作反射通过。不要在共享或生产库重跑已知会导致服务端崩溃的A模式查询。
