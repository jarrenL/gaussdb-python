# JSON、Binary、唯一约束反射修复验证

日期：2026-09-05。本次针对内网 psycopg2 报告中的三个失败项。

## 修复内容

| 问题 | 处理方式 |
|---|---|
| JSON已是Python对象却再次反序列化 | JSON/JSONB结果直接保留DBAPI返回值；JSON字符串、数字、布尔和null同样不会被二次解析。自定义json_deserializer在连接级别注册给驱动 |
| 二进制结果返回十六进制文本 | LargeBinary/BYTEA把hex字符串转为bytes，兼容裸hex及前缀；bytes、bytearray、memoryview按原始数据保留，非法hex明确报错 |
| conkey被字符串化后出现int('[2]') | 统一解析DBAPI列表、元组、数组文本和int2vector；唯一约束、外键及索引共同使用，保留复合列顺序 |

不要求改业务模型、替换数据库或安装公共psycopg2-binary。

## 实际验证

| 环境与范围 | 结果 |
|---|---|
| 本机编译/处理器回归，覆盖两种方言类 | 255通过、1跳过；跳过项为本机原有psycopg3导入检查 |
| Linux aarch64、Python 3.11.15、官方psycopg2 2.9.10 wheel、SQLAlchemy 2.0.43、MYSQL库：原26条基础真实库测试 | 25通过、1失败，无跳过 |
| 同一psycopg2环境：新增4条专项真实库测试 | 4通过，无失败、无跳过 |
| Linux aarch64、Python 3.9.9、gaussdb纯Python实现、SQLAlchemy 2.0.43、MYSQL库：原JSON/二进制用例和新增4条专项测试 | 6通过，无失败、无跳过（其余24条未选取） |
| 方言wheel构建 | 成功，包含新增types.py |

官方psycopg2运行使用wheel自带libpq，Python及依赖隔离在容器临时目录；
未改变数据库角色、认证或系统库。被测base.py、types.py、专项测试文件与
当前工作区SHA256一致。测试完成后未遗留gdb_sa_live_*测试表。

psycopg2基础测试唯一剩余失败：`test_unique_constraint_and_integrity_error`
在CREATE TABLE阶段触发服务器“Global secondary index ... GTM-Lite”限制，
尚未进入反射。新增专项测试将分布键包含在唯一约束中，已实际验证重复插入
抛IntegrityError、单列唯一约束反射及复合列顺序均正确，没有跳过或吞掉异常。

这证明本次三个缺陷的修复在上述环境有效；不代表内网EulerOS x86_64 /
Python 3.12环境或所有兼容模式已通过验收。之前发现的模式名称识别、
其他模式的类型和服务器能力差异不在本次三个修复范围内。

## 内网复测

更新分支源码后，重新构建并安装方言wheel（底层官方psycopg2 wheel保持不变）：

```bash
python -m build --wheel gaussdb_sqlalchemy
python -m pip install --force-reinstall --no-deps \
  gaussdb_sqlalchemy/dist/gaussdb_sqlalchemy-0.1.0-py3-none-any.whl
```

版本号仍为0.1.0，需force-reinstall以避免pip保留旧安装。应用进程也需要重启。
按[Linux双驱动启动](Linux双驱动启动.md)配置环境和GAUSSDB_TEST_URL后执行：

```bash
# 默认运行26条基础 + 4条专项；不要仅重复原来的26条。
bash gaussdb_sqlalchemy/tools/run_driver_test.sh psycopg2

# 只复测本次相关路径（含原始唯一约束用例）
bash gaussdb_sqlalchemy/tools/run_driver_test.sh psycopg2 \
  -k 'json or binary or unique_constraint'
```

专项测试包括JSON对象/标量、自定义解码器、二进制类型及所有字节值、
唯一约束和复合顺序。报告中请分别记录测试通过、建表限制与其他失败，
不能将环境限制记作通过。
